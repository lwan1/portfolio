LLM Fine-Tuning & LLM-as-Judge

Fine-tuned a 1.2B-parameter LLM (Liquid AI LFM2) to speak in a target style using LoRA, then built an LLM-as-a-judge evaluation pipeline with Gemini 2.5 and Comet Opik to score and improve the model quantitatively.

Overview

This project walks the full LLM lifecycle: tokenization and chat templating, autoregressive generation, parameter-efficient fine-tuning with LoRA, and — crucially — evaluation. The base model is Liquid AI's LFM2-1.2B.

The model is fine-tuned to answer in a distinct style (first a leprechaun, then Yoda). Because "good style" is subjective, I used the LLM-as-a-judge pattern: a larger model (Gemini 2.5 Flash) scores generations against the target style, turning a qualitative goal into a quantitative metric.

Goals
  • Understand BPE tokenization and ChatML-style prompt templating.
  • Run next-token prediction and full generation with model.generate().
  • Apply LoRA adapters to fine-tune ~1B parameters efficiently.
  • Mask the loss so only answer tokens are trained on.
  • Build a judge-based metric and use it to iterate on the model.
Results
  • LoRA trains under 1% of parameters yet visibly shifts the model's voice into the target style.
  • Judge scores cleanly separate the three controls: base (low) < generated (mid–high) < true style (high).
  • Style fine-tuning lowers the cross-entropy (negative log-likelihood) of held-out target-style text.
  • Opik tracing logs every live inference call with its style score for monitoring.
Key Learnings
  • Templates and special tokens are what let a base LM behave like a chatbot.
  • Masking question tokens (training only on answers) is essential for instruction-style tuning.
  • A judge LLM is only as good as its system prompt — the prompt defines the rubric.
  • Benchmarks can mislead; synthetic, judge-based evaluation offers a flexible alternative.

LoRA — Low-Rank Adaptation

Instead of updating a weight matrix W directly, LoRA freezes it and learns a small low-rank update BA (rank r=8) applied to the attention and MLP projections (q/k/v/o_proj, gate/up/down_proj). Only those adapters train — a tiny fraction of the model — optimized with the Lion optimizer at lr=1e-4 for 200 steps.

Masked Causal Loss

Each example is wrapped in the template user … <|im_end|> assistant …. An offset mask flags which tokens belong to the answer, and cross-entropy is computed only on those answer tokens — so the model learns to produce styled responses, not to memorize the questions.

Technical Challenges
  • Computing the answer-token mask from tokenizer offset mappings to exclude the prompt from the loss.
  • Fitting a 1.2B model into limited memory — solved by LoRA's tiny trainable footprint.
  • Designing a judge system prompt strict enough to discriminate true style from mimicry.
  • Parsing the judge's JSON score reliably (retry logic over up to 20 attempts).
  • Evaluating subjective style without ground-truth labels.
Configuration
  • Base: LiquidAI LFM2-1.2B; tokenizer uses byte-pair encoding (BPE).
  • LoRA: rank 8, targets q/k/v/o & gate/up/down projections, CAUSAL_LM.
  • Optimizer Lion, lr 1e-4, 200 steps, context length 512.
  • Judge: Gemini 2.5 Flash via OpenRouter; evaluation + tracing via Comet Opik.
Future Improvements
  • Tune LoRA rank, learning rate, and step count against the judge metric.
  • Use multiple judges or self-consistency to reduce judge bias.
  • Add reference-based metrics alongside the judge for triangulation.
  • Explore DPO / preference optimization for finer stylistic control.
Technologies
  • PyTorch, HuggingFace Transformers & Datasets, PEFT (LoRA).
  • Lion optimizer, cross-entropy with token masking.
  • OpenRouter (Gemini 2.5 Flash), Comet Opik evals & tracing.
  • Browser demo: vanilla-JS tokenizer viz, style scorer, Chart.js.
